# 碳惠陇原 · 消费者端与管理端数据统一说明

> 本轮在保留上一轮后台管理系统全部页面/交互的前提下，打通了消费者端与管理端的数据源，
> 使两端共享同一份真实后端数据。本文说明架构、边界、账号与验证方式。

## 1. 问题与目标

- **改造前**：消费者端(`src/api/`)走 Vite 代理 → FastAPI 8000 → SQLite，数据是 UUID；
  管理端(`src/console/api/`)全部读写 `localStorage` 的 `tanhui_console_db_v1`，数据是 `p001/o001`，两端零关联。
- **目标**：消费者端的查询/提交/状态变化在管理端可见，管理端的修改能反映到消费者端。

## 2. 方案：后端权威 + 投影桥

保持管理端页面与 mock 类型不变，新增桥接层 `src/console/api/bridge/`：

| 文件 | 职责 |
|---|---|
| `client.ts` | 管理端专用 HTTP 客户端，独立 token，演示账号自动换取后端 JWT，失败安全降级 |
| `identity.ts` | 后端 UUID ↔ 管理端 mock ID 的持久化映射表 |
| `mappers.ts` | 后端 DTO → 管理端类型的字段映射 |
| `sync.ts` | 拉取后端权威实体并投影到本地数据源；`writeThrough` 写穿透助手 |
| `index.ts` | 统一出口，读取前 `ensureSynced()` 增量同步（30s 节流） |

**读路径**：管理端 `adminApi`/`merchantApi` 的列表类方法开头 `await ensureSynced()`，
拉取后端订单/商品/退款/公告/商家/店铺/分类，映射到本地数据源后交给原逻辑分页筛选。
后端不可达时不影响 mock 演示数据。

**写路径**：关键操作先穿透后端，成功后再更新本地（后端失败即阻断，杜绝"假审批"）：
- 商家入驻申请（消费者端 `merchantApi.apply`）`POST /merchant/apply`
- 管理员审批商家 `POST /admin/merchants/{id}/review`
- 商家商品新建/编辑 `POST|PATCH /merchant/products`、提交审核 `/{id}/submit`、上下架 `/{id}/list|delist`
- 管理员审批商品 `POST /admin/products/{id}/audit`（approve/reject/remove）
- 管理员售后仲裁 `POST /admin/refunds/{id}/handle`（refund→approve）
- 商家发货 `POST /merchant/orders/{id}/ship`
- 公告创建 `POST /cms/announcements`、发布/下线 `POST /cms/announcements/{id}/publish|offline`

**token 隔离**：桥接层按角色分别存储 JWT（`..._token_admin` / `..._token_merchant`），
使"admin 读同步(`/admin/*`)"与"merchant 写穿透(`/merchant/*`)"互不干扰。

**消费者端**：`NoticesView`/`CatalogView`/`account/OrdersView`/`account/LogisticsView`
增加了 `useRefreshOnFocus`，切回标签页自动刷新，管理端改动即时可见。

## 3. 数据归属边界

| 实体 | 权威源 | 说明 |
|---|---|---|
| 订单/店铺子单/物流 | 后端 | 投影为 `r001...`，与演示订单 `o001...` 共存 |
| 商品/SKU/上下架 | 后端 | 投影为 `g001...` |
| 退款/售后 | 后端 | 投影为 `z001...` |
| 公告（已发布） | 后端 | 管理端新建公告先在后端建草稿，发布时穿透 |
| 分类 | 后端(只读) | 后端无写端点，新增/编辑仍走本地 |
| 结算/提现/审计/角色/产地/积分规则 | 本地 mock | 后端无对应端点或无完整字段，保持演示 |

## 6.1 端到端业务流程验证（审批链不跳过）

按「商家入驻 → 审批商家 → 商家上架 → 审批商品 → 消费者购买 → 售后审核」顺序，
每一步都通过 UI 操作并核验后端落库，脚本见 `scripts/flow-step*.mjs`，命令 `npm run flow:*`：

| 步骤 | 命令 | 关键验证 | 结果 |
|---|---|---|---|
| 1 商家入驻申请 | `flow:1-apply` | 消费者 `/join` 提交 → 后端 `POST /merchant/apply`，状态 `pending_review` | 5/5 |
| 2 管理员审批商家 | `flow:2-merchant` | 管理端点审核通过 → 后端 `/admin/merchants/{id}/review` 200，状态 `approved`，自动建店 | 5/5 |
| 3 商家提交商品 | `flow:3-listing` | 商家端发布商品提交审核 → 后端落库 `pending_review`、`is_listed=false`，消费者端暂不可见 | 7/7 |
| 4 管理员审批商品 | `flow:4-product` | 管理端点审核通过 → 后端 `/admin/products/{id}/audit` 200，状态 `approved` | 5/5 |
| 4b 商家上架 | `flow:4b-list` | 后端强制 `approved` 才可 `list`；上架后 `is_listed=true`，消费者可见 | 4/4 |
| 5 消费者购买 | `flow:5-purchase` | `/products?page=2` → 详情 → 立即购买 → 结算 → 沙箱支付，后端订单 `paid` | 10/10 |
| 6a 商家发货 | `flow:6a-ship` | 商家端发货 → 后端子单 `shipped`，消费者物流含快递单号 | 4/4 |
| 6c 消费者申请退款 | `flow:6c-refund` | 消费者提交 → 后端退款单 `requested` | 3/3 |
| 6d 管理员仲裁 | `flow:6d-arbitrate` | 管理端支持退款 → 后端 `/admin/refunds/{id}/handle` 200，退款单 `refunded`，消费者可见 | 4/4 |

> 说明：后端商品状态机要求 `submit(商家) → audit(管理员) → list(商家)`，
> 即"上架(list)"发生在审批之后且必须已审批，这是审批闸门的一部分，不是绕过。
> 每步状态存于 `scripts/flow-state.json` 串联。

## 7. 约束与后续

  后续如需完全权威化，需先补后端 API。
- 演示环境 SQLite 相对路径基于 uvicorn 启动目录；实际联调后端在桌面
